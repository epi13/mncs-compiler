# MNCS Native Application Readiness: Test conversion assessment

**Assessment date:** 2026-10-14
**Candidate tool:** `mncs-test`
**Current recommendation:** Continue with `mncs-test` as the first tool-conversion target, beginning with its native-first verify and digest path. Keep the production host orchestration in place until a native replacement proves full parity.

## Evidence boundary

This assessment is based on the read-only `mncs-test` checkout at `f9575e09ec3481c0ded52bb9e3ec72940725aff6` (`main`, tracked-clean), Compiler producer commit `7d1554e5b3cad480ddac1669c9c16b791ff5728a`, and Gate A evidence `ev_native_app_selected_callable_gate_a_20261014` (`evidence/native-app-readiness-gate-a.json`, SHA-256 `0671b15cb32f635410c7cd8decbcad2bf410861faa4556fcf6ebe9ef8201bd9a`). The Stage-0 probe executable was SHA-256 `f44793c79cd47bce005db5d948b4f35509ad24650676bdc8fa61770825800411`; the canonical VM source revision was `1c19a94732c9d24029dd00e2d5af13710f481d02` and binary SHA-256 `2f7bd4a9f6b537b17e4c1dbf08bcc8cd55362a3f9f1bc28bd91a265a30e1e7f5`.

The real application has one root module and four imported `mncs.test` modules: assertions, suite, generative, and snapshot. It builds a verified `mncs.compiler.application-build/3` VM artifact with a typed request/result interface, nominal records, finite payloads, branching and matches, a bounded sequence, and explicit generic specializations. The selected export set is exactly the `run` entry and the two requested specializations. Two uninstantiated generic templates remain visible in `unselected_unresolved_exports`; they do not enter the selected entry's unresolved obligations.

The Stage-0 project oracle and canonical VM agreed on the structured report and on both typed error results. An invalid record projection was rejected with `MNE162`. The app compile request measured 0.587 s wall / 0.55 s CPU cold (60.1 MB peak RSS, 4 FDs) and 0.020 s wall / 0 CPU warm; the warm result reused the exact verified artifact identity. Canonical VM execution measured 0.179 s wall / 0.17 s CPU (27.6 MB peak RSS, 4 FDs). Cgroup memory was unavailable in the probe. These measurements cover this application request and selected VM, not the full `mncs-test` command or a production workload envelope.

## What can be retired now

No production host implementation is ready for removal from this evidence. The native policy modules are already the authority on the canonical native-first paths; the remaining host code carries OS services, compiler/runtime integration, result transport, Store persistence, or the explicitly supported compatibility path. The concrete near-term cleanup is to prevent duplicate policy from growing in the compatibility adapter and to add parity tests that let individual compatibility behaviors be retired once their replacement is complete.

## Prioritized next steps

1. Use the selected-entry producer contract in the canonical `mncs-test` native runner, then test the full compile-once, retained-session, identity-bound batch path with its existing provider receipt checks.
2. Add dependency-aware verified-fact reuse for this real multi-module application. Current exact warm reuse is whole-artifact reuse; a changed function or dependency still needs bounded invalidation and reused proof evidence. Repeat cold, warm, changed-function, changed-dependency, invalid-source, and interrupted-build experiments on this workload.
3. Obtain approved Language and Compiler-main scopes before cross-repository implementation or delivery. Add bounded file/process capability contracts only when the actual runner needs them; keep `mncs test` manifest and OS boundaries explicit.
4. Wire compiler outputs through the existing Test/Forge/Monitor/Store authorities and prove receipt provenance and measured resources. Do not implement a parallel scheduler, persistence layer, or process manager.
5. Retire compatibility host code one behavior at a time only after the native command passes its parity corpus and the remaining caller population is known.

Gate A passes for this useful native application. Gate B is partial, Gate C has a versioned producer contract but no end-to-end consumer integration, and Gate D is an actionable assessment rather than a claim that the complete tool is ready to replace.
